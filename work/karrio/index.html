Building Karrio as a platform

Open shipping infrastructure that other teams can build on.

Founder & CEO, 2020–2026
Currently architect and product engineer at JTL-Software

I started Karrio as an open-source shipping platform. The company followed in 2020.

The product decision

I chose to design Karrio as a platform. The alternative was a conventional shipping aggregator or multi-carrier SaaS product. I designed the product for teams building shipping into their own software.

That meant making shipping programmable and giving integrators tools to understand what their integration was doing. Stripe influenced the developer experience and the way API activity is presented.

The developer tools include API logs with request and response details. A developer can inspect an individual transaction while working through an integration.

Where the differences go

A rate request enters Karrio through a shared model. A carrier plugin translates the request into that carrier’s schema, then maps the response back into rates and messages.

The integration handles carrier-specific service codes and options. For an application using Karrio, the request and response follow the same model across carriers.

Implementation reference: Karrio’s plugin development guide.

A platform other people can extend

The constraint that decides most of the design is whether someone I have never met can extend it without me in the loop.

Carrier plugins follow a documented structure. A new integration supplies its translation and connection logic through the plugin interface.

That gives another developer a defined place to add a carrier. The shared platform can remain useful as the set of integrations changes.

The company around it

Karrio has an LGPL community edition and a commercial tier. JTL-Software acquired Karrio in 2025, and it now provides shipping inside JTL’s commercial stack.
